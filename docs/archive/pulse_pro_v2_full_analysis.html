Gap #3 — _format_story doesn't return posts with content
ArticleRepository._format_story() returns "platforms": [c.platform for c in article.generated_contents] — a list of platform names only. But StoryCard.jsx checks story.posts?.find(post => post.platform === p) expecting objects with .content and .posted. Since story.posts is undefined (the API returns platforms not posts), the StoryCard always falls back to fetching content via the API — which is slower and more fragile. Fix: add "posts": [{"platform": c.platform, "content": c.content, "posted": c.posted} for c in article.generated_contents] to _format_story().
Gap #4 — Two parallel LLM code paths causing confusion
You now have two LLM systems: the old backend/llm.py (used by processors and generators via get_llm_client()) and the new backend/llm/ module (used by SmartLLMRouter). They are completely separate. The old system has the dual cache. The new system is clean. Most of your pipeline still uses the old system. Until you migrate processors and generators to use SmartLLMRouter, the new architecture is unused.
